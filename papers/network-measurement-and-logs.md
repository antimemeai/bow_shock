# Network measurement, logs, and replay fixtures

Research lane, 2026-10-01. This extends [network observation and editing](network-observatory.md), [privacy/fingerprints](fingerprints-and-privacy.md), and [native browser surfaces](native-browser-surfaces.md). It studies measurement references for Bow Shock's dedicated human-agent browser, request/response workbench, tracker alerts, and deliberate external network experiments. This lane ran no collector, server, proxy, packet capture, model service, or reference test. These are study references, not selected dependencies.

The central requirement is an observation with a stated boundary: **what the browser attempted, what was actually captured, what the server received, and what the page showed are distinct facts**. A missing response body is not an empty response. A changed tracker configuration is not evidence of changed information collection. A replay that renders correctly is not a reproduction of the original connection or remote server state.

## What privacy measurement systems actually record

The original OpenWPM paper explains stateful browser measurements and joining browser, network, and disk observations by site visit/browser identity. Its design motivation remains relevant: a stripped-down browser can miss resources and features, and a stateless profile changes the experiment. Its January 2016 crawl and then-current proxy/Firefox architecture are historical evidence, not the current engine contract. [Englehardt and Narayanan, extended CCS 2016 paper](https://senglehardt.com/papers/ccs16_online_tracking.pdf).

Current pinned OpenWPM uses Firefox extension HTTP listeners. Its event assembly joins request headers/body, response metadata/body, and redirects; `shouldSaveContent` filters by configured resource type. Schema fields include visit/browser identity, POST body/raw body, response cache state, and content hash. A redirect construction still has a nullable new request ID with a TODO rather than pretending a complete redirect join. README explicitly asks researchers to record OpenWPM version because instrumentation changes or bugs can affect results. [Pinned HTTP instrument](https://github.com/openwpm/OpenWPM/blob/ae85559ac9c500448c3bddeaed0c1380664aea53/Extension/src/background/http-instrument.ts), [version guidance](https://github.com/openwpm/OpenWPM/blob/ae85559ac9c500448c3bddeaed0c1380664aea53/README.md).

A specific source concern deserves a future direct oracle: `ResponseBodyListener` concatenates incoming chunks into a body, but calls `digestMessage(incoming).then(this.resolveContentHash)` for each chunk. The hash Promise therefore appears to settle on one chunk's digest, whichever asynchronous digest resolves first, rather than a digest of the concatenation. Its reviewed listener also resolves body at `onstop`, with no explicit `onerror` settlement branch. This is a **tentative static observation at the pin**, not reproduced behavior or a claim about published datasets. Before relying on it, inspect caller/error lifecycle and check a known multipart binary response against independently known bytes. [Pinned listener, lines 23–37](https://github.com/openwpm/OpenWPM/blob/ae85559ac9c500448c3bddeaed0c1380664aea53/Extension/src/lib/response-body-listener.ts#L23).

Krumnow, Jonker, and Karsch studied OpenWPM detectability, detection prevalence, and recording integrity; their 2022 study found detection on approximately 14% of front pages in a 100,000-site crawl and attacks/evasions against instrumentation. The rate belongs to that historical experiment. The transferable result is to characterize the observer's effects and integrity rather than assume measurement is transparent. [Primary paper](https://arxiv.org/abs/2205.08890).

Tracker Radar is a periodically updated dataset of third-party domains and resources, explicitly **not a blocklist**. Regional top-site samples, ownership, prevalence, cookie/API observations, resource patterns/hashes, and breakage exceptions are useful priors for an alert. A domain's score is a crawl-derived assessment of API use, not a finding that the request just seen fingerprinted this user. Unlisted domains remain unknown; a listed CDN/shared domain can serve multiple purposes. The data license is NC-SA; study does not select shipment rights. [Pinned model](https://github.com/duckduckgo/tracker-radar/blob/c958f33e5d892e82d9b150d548793920286d6fc2/docs/DATA_MODEL.md), [FAQ](https://github.com/duckduckgo/tracker-radar/blob/c958f33e5d892e82d9b150d548793920286d6fc2/docs/FAQ.md).

Its collector provides a useful counterexample to a lossless workbench. `RequestCollector` handles out-of-order extra-info events and repeated redirect request IDs, copies redirect responses into each hop, and tracks failure reasons. Its exported records include filtered response headers and a body hash, but omit request bodies, most headers, and internal request IDs; it records WebSocket creation without a message transcript. Hash retrieval failure returns null. Binary base64 content is converted to UTF-8 text before SHA-256, so that hash is not general byte identity. These choices suit one study; Bow Shock should keep different capture claims. [Pinned collector](https://github.com/duckduckgo/tracker-radar-collector/blob/4ad2472b346bf9b544ca4815db29266e3a8369d5/collectors/RequestCollector.js).

The API-call collector attaches debugger instrumentation/breakpoints and evaluates injected code; it is useful to study attribution, but cannot be automatically adopted as a native-only DOM observer or assumed to preserve timing/fingerprint behavior. Separate normal session capture from more invasive experiment instrumentation. [Pinned API collector](https://github.com/duckduckgo/tracker-radar-collector/blob/4ad2472b346bf9b544ca4815db29266e3a8369d5/collectors/APICallCollector.js).

## HAR, WARC, and the identity of a body

HAR is a useful exchange format, not the authoritative session model. The inspected schema requires response size/MIME metadata while response `content.text` remains optional. Therefore a valid HAR can omit bodies. Timings may be unavailable; do not coerce unknown values into measured zero. These maintainer schemas also contain `min` rather than JSON Schema's standard `minimum` keyword in some numeric definitions, another reason structural validation alone cannot supply the semantic oracle. Haralyzer's request text accessor can return `_textBase64` without decoding; response text/encoding are separate properties, and its response text accessor assumes `content.text` exists. Check format adapters before using an absent value or text hash as byte evidence. [Content schema](https://github.com/ahmadnassri/har-schema/blob/c01b2e49edc33cd2cd22c980c57681be57bbb1f6/lib/content.json), [timings schema](https://github.com/ahmadnassri/har-schema/blob/c01b2e49edc33cd2cd22c980c57681be57bbb1f6/lib/timings.json), [Haralyzer accessors](https://github.com/haralyzer/haralyzer/blob/29ffe0d2e26dc97b2adaa329328beb228ba8c356/haralyzer/http.py).

Chrome DevTools defaults to sanitized HAR without Cookie, Set-Cookie, or Authorization headers and offers sensitive-data export. This is a useful default, but it does not establish removal of sensitive query strings, POST fields, response content, or nested tokens. Existing `network-devtools-reference` records this official source. The original HAR author specification failed to fetch through both HTTP/HTTPS in this pass; the catalog retains that gap. [DevTools Network reference](https://developer.chrome.com/docs/devtools/network/reference).

WARC distinguishes record block and payload digests, captures timestamps/IDs, supports request/response/revisit/conversion records, and has explicit truncation metadata. A revisit may depend on an earlier record; archive completeness is about the needed record graph, not merely a ZIP opening successfully. Community annotations on the IIPC specification are explicitly not ratified standard text. WACZ packages archives, indices, and page information; it does not itself certify replay fidelity. [WARC 1.1 annotated specification](https://iipc.github.io/warc-specifications/specifications/warc-format/warc-1.1-annotated/), [WACZ 1.1.1](https://specs.webrecorder.net/wacz/1.1.1/).

warcio exposes raw streams and a `content_stream()` that decompresses/dechunks HTTP payloads. Keep a digest's representation alongside the digest: wire-encoded bytes, decoded entity bytes, Unicode text, redacted text, and rewritten archive content must not share an unlabeled “body hash.” Hashing a redacted derivative answers a different question from hashing the original response. [Pinned warcio guide](https://github.com/webrecorder/warcio/blob/2a797aa8c6d67e70966ce9d1a690208ab250fbe7/README.rst).

pywb deliberately rewrites resources for archival replay. Its recorder supports skip/dedup/filter policies: pinned `SkipRangeRequestFilter` skips ranges except those beginning `bytes=0-`; `ExcludeHttpOnlyCookieHeaders` removes all Cookie request headers and only HttpOnly Set-Cookie headers. Those filters do not redact arbitrary payloads. Existing replay tests exercise archive application behavior, not a Chromium/OS interruption experiment. [Pinned recorder filters](https://github.com/webrecorder/pywb/blob/55cf079c80fe73597689180953992fe5028f0d39/pywb/recorder/filters.py), [replay tests](https://github.com/webrecorder/pywb/blob/55cf079c80fe73597689180953992fe5028f0d39/tests/test_record_replay.py).

Browsertrix's pinned recorder preserves binary base64 as bytes, unlike the collector above, but may directly refetch failed media and rewrite selected media/HTML/JS responses, marking rewritten content. An archive can therefore include useful recovered content that differs from what the original page received. Its QA compares screenshot pixels, extracted text, and page resource outcomes; these dimensions complement each other but do not show equal tracker payloads, cookies, remote effects, or timing. [Recorder implementation](https://github.com/webrecorder/browsertrix-crawler/blob/663cd8c41f1e377eb0b719f6705af2b28c7f7863/src/util/recorder.ts), [QA methods](https://github.com/webrecorder/browsertrix-crawler/blob/663cd8c41f1e377eb0b719f6705af2b28c7f7863/docs/docs/user-guide/qa.md).

WARC-Bench is a pertinent evaluation precedent: archived short GUI tasks with programmatic end-state checks. Its methodology explicitly limits replay to captured/renderable interactions, describes unarchivable sites and timestamp/random/session-ID URL difficulties, and manually checks generated tasks/evaluators. Those limitations are more useful than the broad high-fidelity claim. For Bow Shock, archived widgets can test bounded human-agent interaction, while an owned live server is needed for authoritative network effects. [Paper, environment and collection sections](https://arxiv.org/html/2510.09872v1).

## Baseline and alert method to pressure-test

The following is a research proposal, not a settled design. Keep three linked records: capture events with provenance/completeness, a normalized comparison view with policy version, and an alert judgment citing actual differences. Preserve enough provenance to explain why a value was excluded. Model-readable derivatives should be redacted before judgment; a model must not choose how much raw session data it gets.

| Baseline axis | Context needed | Meaningful comparison |
| --- | --- | --- |
| Runtime | Engine/build/platform, capture protocol/version, target/frame/document generation | Compare within cohort; mark engine or observer migration explicitly |
| Session | Login/consent, cookie/cache/storage state, service workers, locale/time zone, region | Distinguish state and consent changes from script/config drift |
| Workflow | Page/site, user action, initiator/resource type, redirect hop, observation interval | Align equivalent steps; preserve causal ordering and repeated sends |
| Request | Method, destination/owner, path, query/body field names/types and disclosed classes | New field/destination/event; changed cardinality, encoding, method or consent use |
| Response | Status, headers, body representation/digest, script/config version | Changed response/config; separate cache hit, changed bytes and unavailable body |
| Intervention | Actual outside-browser intervention time/type, connection/failure/retry, server effects | Compare unaffected control with intervention; do not infer reduced tracking from errors alone |

For Meta Pixel, distinguish script/config downloads (such as observed Facebook.net resources), the Facebook.com `/tr` event endpoint, first-party cookies, consent state, and request-body/query field structure. Tracker Radar supplies classified resource patterns; PixelConfig supplies historical configuration drift methods. Neither substitutes for the current Meta wire-field contract, whose primary documentation remains an acquisition gap in the earlier lane. Alerts can truthfully say “new field class/endpoint/extra retry observed” without asserting what Meta inferred.

Normalize date/nonces/identifiers only through an explicit learned-and-reviewed variability policy. A dynamic identifier can be the privacy-relevant fact: suppressing its exact value should retain its presence, type, length class, origin, and within-session equality where justified. Keep counts and order for redirects/retries/events; group interchangeable parallel static assets separately. Timing baselines need repeated samples, comparable workload and spread, not a single golden trace. Report observation coverage and sample count next to a change.

DeepDiff can exclude paths, ignore selected sequence order, report repetitions, and apply numerical precision/tolerance. Its docs show bounded matching passes can affect results. These are comparison mechanics, not domain truth: globally ignoring order/repetition can erase retry storms or consent-before-send violations, and broad numeric rounding can hide changed event values. Prefer stable keyed request groups plus separate sequence/count comparisons; signal incomplete matching. [Pinned order documentation](https://github.com/qlustered/deepdiff/blob/79e4379278b1cfdd8e9e3dccac364956908e8989/deepdiff/docstrings/ignore_order.rst), [exclusions](https://github.com/qlustered/deepdiff/blob/79e4379278b1cfdd8e9e3dccac364956908e8989/deepdiff/docstrings/exclude_paths.rst), [numeric semantics](https://github.com/qlustered/deepdiff/blob/79e4379278b1cfdd8e9e3dccac364956908e8989/deepdiff/docstrings/numbers.rst).

Storage/redaction precedes JEV or onboard-model interpretation. Proposed handling: bounded capture retention; session-separated restricted raw bodies where deliberately needed; redacted structural metadata for ordinary alerts; secret-header/query/form/body filtering; explicit treatment of unknown MIME/binary payloads, compressed data, nested credentials, hashes of personal information, screenshot text, and archive sidecars. Redaction can leave equality tokens for necessary comparison, but these remain linkable data; plain hashing does not anonymize customer information. Redacted and raw artifacts need independent identities and explicit transformation versions. Export/replay packages should inherit the same policy, rather than bypass it through WARC metadata or page screenshots.

A typed judgment candidate is `expected_variation | runtime_or_session_change | resource_or_config_change | new_data_disclosure | transport_or_capture_failure | unknown`, with evidence references, comparable-baseline count, missing coverage, and a bounded explanation. Categories may coexist. “Unknown” is required when capture cannot distinguish suppression, caching, failed body retrieval, and non-occurrence. JEV can prioritize/explain already redacted deltas; it cannot certify what a remote tracker inferred or silently alter browser traffic. This lane made no judgment calls.

For implementation research, independent category flags fit separate Noul
questions; an exclusive reviewed routing status fits Choice. The root's
[separate constructed Jev pilot](jev-network-judgments.md) exercised three
exclusive advisory alternatives. Its results do not evaluate this lane's broader
multi-label proposal or real capture accuracy.

## Owned fixtures and external evidence

HTTPBin's pinned Python routes cover request reflection, status codes, redirects, cookies, cache, delayed replies, streamed JSON, drip responses, and seedable random bytes. go-httpbin's reviewed delay/drip code watches request-context cancellation, exposes Server-Timing, and distinguishes Content-Length drip from chunked stream routes. A server's attempted 499 after cancellation need not be received by the client. Seeded bytes plus exact configured headers/body provide a direct capture oracle; a random public response does not. [Python routes](https://github.com/postmanlabs/httpbin/blob/f8ec666b4d1b654e4ff6aedd356f510dcac09f83/httpbin/core.py), [Go handlers](https://github.com/mccutchen/go-httpbin/blob/34888fd21d6667e9f0c842db483ba595b9c8c094/httpbin/handlers.go).

http-echo is intentionally simpler: known startup text/status/version headers and request access logging. Its `metaResponseWriter.Write` assigns length from each write rather than accumulating total writes, so that log is not a general stream-byte oracle. WireMock's fault tests assert concrete reset, absent-response, and malformed-chunk client exceptions. Official docs warn reset behavior depends on OS. These fixtures produce server-side faults/delays; they do not reproduce changing the host's route/interface while Chromium experiences its normal OS networking environment. [Echo handlers](https://github.com/hashicorp/http-echo/blob/767bbd9c3d1905acb04891d5c5e208de17b34a71/handlers.go), [WireMock tests](https://github.com/wiremock/wiremock/blob/fafa0a9f76c7086b76d892f0b4c5f22cc8dc4433/src/test/java/com/github/tomakehurst/wiremock/FaultsAcceptanceTest.java), [fault docs](https://wiremock.org/docs/simulating-faults/).

A future owned fixture matrix should directly cover ordinary complete bodies, binary/chunked/empty responses, multiple redirects, cache/304, request uploads, duplicated event IDs, CORS/preflight, workers, long-running streams, partial transfer and reconnect. Join the server's known received events with browser capture and intervention timestamps. Separately judge whether the page task remained usable. No downloaded test's success substitutes for these specific native runtime outcomes.

Zeek offers independent network-layer context: connections include UID, endpoint tuple, history, reset states, packet/byte counts, and content gaps; HTTP records add transaction depth, host/URI/method/status and body lengths when HTTP is visible. Its TLS/QUIC metadata complements browser observations, but passive capture does not natively expose encrypted HTTPS bodies, and ECH can hide the destination name. A connection UID is not a browser request ID; HTTP multiplexing, reuse, caches, workers and encrypted DNS make joins partial. Captured gaps describe the observer's visibility and must not automatically be equated with server/application loss. [Pinned connection schema](https://github.com/zeek/zeek/blob/82d9bcbe7756c49bdde666341944d53ff15ee935/scripts/base/protocols/conn/main.zeek), [TLS visibility docs](https://docs.zeek.org/en/current/reference/logs/ssl.html).

The open questions are precise: which native session surfaces cover each request class; what happens to body capture under streams/eviction/crashes; which baseline variability is stable across real human sessions; whether redacted deltas retain useful disclosure evidence; which replay interactions are complete; and how actual OS interventions change browser/page/server signals. These need design and owned experiments. No reviewed source establishes undetectability, site acceptance, or a reduction in tracker inference from traffic perturbation.
