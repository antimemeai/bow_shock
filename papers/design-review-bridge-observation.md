# Tribunal review: agent bridge and native observation

Review date: 2026-10-01. Reviewed [agent bridge](../docs/design/agent-bridge.md), [runtime observation](../docs/design/runtime-observation.md), [integration](../docs/design/README.md), and the shared control/evidence contracts where they cross these boundaries. This is an independent design review, not implementation testing. Only this report was written; no design fixes, agent execution, OS input, or network changes were performed.

Checked the acquired DOM/DOMSnapshot protocol definitions and local Codex 0.160.0 schema exports directly. The baseline export confirms `outputSchema` constrains the final message, `expectedTurnId` is required for steer, provider capability read has only three named capabilities, and baseline thread start lacks `dynamicTools`. Root's subsequent experimental export establishes that property in the experimental schema; it still does not establish enabled registration or containment. Those source claims do not warrant a finding. Installed binary, acquired Codex source pin, and future CEF release tuple are correctly distinguished.

Severity: **High** means an underspecified boundary can disclose data or violate a stated authority/resource claim; resolve before enabling that capability. **Medium** means a cross-component contract can admit inconsistent interpretations and needs a precise decision before implementation. Findings distinguish a specification gap from an explicitly unverified empirical capability; none asserts an executed exploit.

## BR-01 — High: export lacks a revocation linearization point

**Type:** cross-component specification gap. [Bridge disclosure](../docs/design/agent-bridge.md#observation-and-disclosure) says selection applies before transmission; candidate revocation concerns admission/effects. [Control](../docs/design/control-and-input.md#authority-transitions) revokes action epochs, and [evidence](../docs/design/evidence-and-tables.md#local-evidence-store) requires an independent export scope. None defines which owner rechecks an export grant at the last host-controlled transmission boundary or what queued/partially transmitted exports do after revocation.

**Trace:** a permitted origin's DOM/AX bundle is redacted and queued for a hosted provider while its connection stalls. The human removes that origin or disables export. The action epoch changes and all late proposals are rejected, but the previously prepared payload remains in an adapter queue. Reconnect or the next flush transmits it under its old policy version. All current action checks can pass while the disclosed bytes violate the person's new scope. Treating queueing as already disclosed is a possible policy, but the design does not state that policy or show it to the person.

**Required decision:** name the export owner and its authority/epoch check, define a single host-side admission/transmission boundary, invalidate unsent queued bundles/derivatives on revocation, and distinguish `not_transmitted`, `partially_transmitted`, and `provider_retained_unknown`. Already received bytes cannot be recalled; the specification already acknowledges this and should preserve it. Provider change must not revive the old queue.

**Direct oracle:** a controlled provider accepts headers but blocks body reads while a secret-marker bundle waits. Revoke scope and then unblock/reconnect. Inspect the actual bytes received, queued descendants, and export outcomes. A “grant revoked” UI event alone does not demonstrate the required boundary.

## BR-02 — High: history reconciliation has no acceptance rule

**Type:** security-relevant specification gap, not a claim of provider erasure. The bridge correctly calls resume, fork, compaction, and model switching disclosures and requires reconciliation. [Its Codex baseline](../docs/design/agent-bridge.md#codex-adapter-versioned-baseline-and-experimental-path) nonetheless permits thread resume with provider/model overrides without defining when existing history makes that operation inadmissible.

**Trace:** thread T includes origin A's authenticated records and origin B's public records under an approved provider/account. Later scope is reduced to B, or the person selects a different provider/account with B-only consent. The host validates the new B observation, resumes/forks T, and starts a turn. T's prior messages, summaries, stored tools, and prior model-generated quotations can reintroduce A, even though no new A bundle was supplied. Pagination or server-side compaction can make local history incomplete; recording only observation IDs supplied by Bow Shock does not prove that all provider-held derived context is reconciled.

**Required decision:** define conversation disclosure ancestry, the allowed retention/use distinction, and what evidence permits continued use after a scope/account/provider change. When effective retained history is unknown or outside the new policy, choose a fresh thread with only authorized reconstructed context, or obtain an explicit concrete expanded-history decision. Do not infer that `excludeTurns` removes inference context: the local resume schema describes that option as omitting turns from the response payload. Old provider copies may remain, but they must not silently become approved context for a new workflow.

**Direct oracle:** controlled provider history includes a marker in an old message and in a compacted summary; history listing exposes only a page of items. Tighten scope, switch/fork/resume, and inspect effective turn input plus the selected thread/policy. The oracle distinguishes new transmissions from continued provider use; inability to inspect effective context must cause an explicit unknown/unavailable result rather than a clean-scope assertion.

## BR-03 — High: secret exclusion is stronger than the specified classifier

**Type:** unimplemented policy mechanism with an overbroad invariant. [Runtime sensitive-data handling](../docs/design/runtime-observation.md#representation-visibility-and-sensitive-data) requires excluding password values and authentication/payment secrets across DOM, AX, provenance, and pixels before logging/publication. The documents specify neither an enforceable field classification nor the behavior for private content whose secret status cannot be determined. The ordinary evidence contract's unknown-type withholding addresses unsupported encodings, not secrets embedded in supported visible text.

**Trace:** an authorized page mirrors a password/one-time token into an ordinary `<div>`, accessible live-region name, error message, canvas, or screenshot. Native observation correctly suppresses the original password input, but the mirrored marker belongs to otherwise allowed visible content. A generic password-field filter passes it. A model classifier can also be uncertain or mistaken. This is possible within one origin and does not need an opaque-frame or CDP escape. The person's approval of authenticated page observation does not specify whether such secret echoes are included.

**Required decision:** define which secret classes can be excluded deterministically, explicit policies for sensitive forms/pages and unknown classification, and the actual guarantee. Either conservatively withhold the relevant region/modality/page when exclusion cannot be established, or make a concrete human disclosure choice and narrow the promise to enforced classes. Do not turn an uncertain semantic detector into a guarantee that all authentication/payment secrets are absent. Derived AX/text/pixels must receive the same decision.

**Direct oracle:** owned fixtures echo known markers through password inputs, ordinary text, ARIA descriptions/live regions, URLs, images/canvas, and provider-bound summaries. Inspect actual logged/exported representations, not only the original input node or redaction count. Include intentionally unclassifiable supported text to verify the chosen unknown policy.

## BR-04 — Medium: opaque/unknown origin is represented but grant matching is undefined

**Type:** authority-contract gap. [Runtime identity](../docs/design/runtime-observation.md#identity-capture-and-invalidation) correctly forbids treating serialized opaque origins as shared authority and permits binding them to document incarnation or marking authority unknown. [Shared Grant](../docs/design/control-and-input.md#grant-and-intent-records) describes expected origin scope. Neither specifies matching/consent semantics for the unknown or opaque case.

**Trace:** a named-origin grant contains a sandboxed srcdoc child with an opaque origin. The broker cannot recover a useful origin token and marks it unknown. One implementation treats visible children of the approved tab as included; another treats `null`/unknown as a wildcard; a third refuses it. The first two can export content from another opaque child with the same serialized status or reuse an approval after replacement. The document warns against that mistake, but the inter-service authority operation still lacks a defined result.

**Required decision:** unknown authority does not match a named-origin grant; define a denied/unavailable default. If supported, human approval of an opaque frame must bind the exact surface/frame/document/activation identity, never the serialized origin string. Define inherited about:blank/srcdoc using verified effective origin or this same unknown policy, with explicit new approval after replacement. A screenshot containing denied frames requires its own enforceable disclosure choice or withholding.

**Direct oracle:** two simultaneously visible sandboxed children have distinct secret markers but the same serialized opaque-origin value. Approve only one incarnation; replace it and create inherited about:blank children. Check both native text and pixels supplied to consumers. Correct classification alone is insufficient without correct grant matching.

## BR-05 — Medium: runtime generations are not carried through the shared proposal contract

**Type:** cross-document interface inconsistency, rather than a claim that the design promises atomic input. Runtime identity explicitly distinguishes document incarnation, BFCache activation generation, attachment generation, and node-ID invalidation. [ObservationRef](../docs/design/control-and-input.md#grant-and-intent-records) names document epoch and geometry/layout revision, while [bridge bundles/envelopes](../docs/design/agent-bridge.md#typed-proposals-and-admission) refer to document/frame epochs and observation IDs without declaring how these generations are recovered and compared. The runtime also states that old action eligibility cannot return on BFCache reattachment.

**Trace:** A is observed, navigation activates B, then BFCache restores A's same document incarnation. An old A observation survives in history and is referenced by a fresh proposal under a new live grant. If an executor compares only session/frame/document incarnation and refreshes an otherwise identical semantic target, it cannot prove that this is the required new-activation observation. Separately, inspector node-ID invalidation without an obvious new committed-document identity can leave a persisted node reference looking document-valid. Existing high-level invalidation requirements intend rejection, but different owners can encode the epochs differently.

**Required decision:** define the complete freshness tuple behind `ObservationRef`, including activation/attachment and protocol-node invalidation where relevant, and make evidence lookup supply it to admission and execution. A historical observation can remain readable while being explicitly ineligible for action. Distinguish observation-local IDs from protocol IDs and define invalidation without relying on matching integers. Freshness cannot be established solely by advancing a host presentation counter.

**Direct oracle:** retain observations through BFCache activation, target detach/reattach, protocol document update, and reused node/session lookup values. Submit old references under a fresh grant. Verify no input becomes eligible from them and that a fresh authorized observation is required. The existing non-atomic focus/input race remains a separate measured gate, not this finding.

## BR-06 — Medium: native snapshot budgets do not define an enforceable work bound

**Type:** empirical capability gate that must constrain the implementation claim. Runtime requires independent response-size/traversal/node/time budgets and its scenario table asks that UI/lifecycle remain responsive. It also correctly acknowledges that rejecting an oversized callback cannot undo engine work. The acquired [DOMSnapshot PDL](https://github.com/ChromeDevTools/devtools-protocol/blob/8b7f1d955017db8633ecae04cdfa194f731c9eff/pdl/domains/DOMSnapshot.pdl) returns the full snapshot and has no traversal/node/time limit parameter.

**Trace:** an allowed page contains a very large tree and text payload. `captureSnapshot` performs lifecycle update/traversal/serialization before the host receives bytes. The worker's copied-byte/node bound discards the result, but renderer/DevTools/UI-path work has already occurred. Repeating the read through a bounded per-message API can still monopolize resources; a synthetic malformed-message producer tests host parsing, not the native page-driven work.

**Required decision:** separate post-receipt retention/parsing limits from enforceable native capture-work limits. Establish request concurrency/rate limits and a measured cancellation/watchdog/failure path, or mark large-page native capture unavailable/partial where it cannot meet the operational requirement. Do not advertise a hard renderer traversal/time bound based on host discard or a timeout that only stops waiting. Stop/revocation responsiveness must have a control path that remains available during native observation overload.

**Direct oracle:** actual candidate-binary fixtures grow node count/text/layout complexity while simultaneous Stop and lifecycle events are issued. Measure renderer/native callback work and the independent control response, not merely returned truncation metadata. Existing text already recognizes the uncertainty; this finding requires carrying that gate into capability promotion and the plan.

## Accepted limits and integration assessment

The same-UID distinction is explicit in both README integration and the bridge. A trusted Codex agent can act through its environment's ambient shell/IPC/OS privileges even when Bow Shock exposes only proposal APIs. Malicious page text inducing that agent to use its shell is therefore outside the claimed containment, not evidence of successful gateway enforcement. The no-direct-model-actuation claim applies to the constrained role only. If the operator requires that guarantee for the coding peer too, unrestricted same-UID integration is unavailable until a separate containment design is reviewed. This is an acknowledged product/deployment gate, not a hidden flaw newly established here.

OOPIF routing, CEF/CDP identity mapping, effective-origin provenance, frame/pixel redaction, geometry transforms, capture skew, and sandbox compatibility are already correctly labelled unverified on a candidate binary. The design does not claim that source acquisition proves those behaviors. Likewise, its current-target refresh and residual OS queue race are stated limitations; this review does not invent atomic capture-to-click as a new requirement.

The integration is coherent about proposal versus execution ownership, separate human network powers, useful partial outcomes, and unavailable capability gates. The six findings above concern places where an invariant needs a shared executable meaning before the implementation plan can rely on it. A tribunal disposition should resolve or explicitly reject each trace; a renamed field, new warning label, or extra audit record alone cannot establish export, scope, or freshness correctness.

## Integration recheck — 2026-10-01

Re-read the revised bridge, runtime observation, shared authority, integration README, and [tribunal dispositions](design-tribunal.md) against the original traces. All six findings are resolved at the design level; BR-06 remains an explicit empirical capability gate.

| Finding | Recheck outcome |
| --- | --- |
| BR-01 | The disclosure owner rechecks immutable bundle ancestry, destination, grant and generations at each serialized last host-controlled transport handoff. Revocation drops unsent bundles and retries. Bytes already handed off may arrive later; the named unknown/partial outcomes preserve that limit. The stalled-queue trace is addressed without promising recall. |
| BR-02 | Conservative conversation ancestry covers supplied content and derived summaries/quotations. Continued use requires the entire known history to fit current policy; incomplete or out-of-scope context requires fresh authorized reconstruction or concrete expanded consent. Retention, use and transmission are distinct, and `excludeTurns` is expressly not deletion. |
| BR-03 | The invariant now covers enforced structured exclusions and reviewed projections. Sensitive/unknown regions and unenforceable modalities are withheld; approved routine projections explicitly retain residual unrecognized secret/echo risk. The design no longer promises universal secret absence from arbitrary prose or pixels. |
| BR-04 | Unknown origins cannot match named-origin grants. Opaque consent binds the exact surface/frame/document/activation and representations; replacement requires new approval. Denied-frame pixels require withholding or a separately enforceable reviewed scope. |
| BR-05 | Host evidence resolves the complete attachment/document/activation/node-generation tuple at admission and execution. Historical observations remain readable under retention policy but cannot regain action eligibility through a fresh grant. The BFCache and node-reuse traces now have an explicit rejection rule. |
| BR-06 | Host copy/parsing/retention bounds are distinguished from native renderer work. One native capture transaction and one coalesced refresh limit concurrency; actual overload/Stop measurements gate promotion. Helper control must remain independent of blocked observation callbacks, and unsupported full capture stays unavailable. |

No additional blocking contradiction was found in these revised contracts. The original direct oracles remain implementation acceptance cases, not evidence already obtained. This recheck performed no implementation tests and does not close native routing, projection enforcement, provider-history inspectability, capture overload, or deployment-containment gates. The acknowledged same-UID trusted-peer limit remains unchanged.
