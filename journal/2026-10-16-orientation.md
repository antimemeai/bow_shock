## Proposed sequence

The strongest next product milestone is: the person navigates to an unfamiliar
page in Oxcart, chooses a bounded region and schema, gets grounded rows, corrects
them, Saves and reopens them. This directly extends the existing useful slice
and the operator's learned-extraction requirement. It does not require all
automation and network features before becoming useful.

1. **Reconcile the baseline.** Record the clock build's actual partial outcome;
   resolve the observed reopen/startup condition and finish its direct native
   joins. Qualify the installed Codex version through the external adapter.
   Make the tool invocation reproducible. Retain existing clock simplification
   and avoid inventing a retrospective cause for the old intermittent failure.
2. **Replace the internal representation contract.** Write and review one
   bounded native/controller/store contract, then implement owned native types,
   binary IPC and binary/typed SQLite persistence. Retain external protocol
   adapters and existing direct oracles for exact review, disclosure, expiry,
   Stop and clean reopen. Add no general codec framework or compatibility lane.
3. **Broaden read-only observation through a narrow supported workload.**
   Remove the dependency on known field IDs by exposing selected structure and
   source-backed candidate regions. First qualify unfamiliar top-level pages,
   freshness under navigation and explicit hidden/form/frame/oversize handling.
   Keep unsupported frames and modalities explicit. Measure real capture work
   and UI servicing; a larger callback limit does not qualify arbitrary pages.
4. **Deliver unfamiliar-page extraction, then teaching.** Choose one useful
   listing/detail family and a reviewed schema. Extract repeated rows with
   grounded fragments and explicit ambiguity, review/correct/Save/reopen. Then
   retain a small owned page-family rule representation learned from corrections
   and exercise unseen pages and layout changes. Wrong fields must produce a
   reviewable mismatch; success includes operator correction effort.
5. **Probe input and network feasibility early, then integrate each separately.**
   Native focus/permission/receiver/takeover and confined macOS packet/path
   feasibility should not wait behind extraction polish. Enable OS gestures
   only after actual receiver/Stop/drain outcomes. Implement passive exchange
   capture before baselines, request composition, pause ownership and existing
   response-body editing. Preserve the full product's external packet and
   native-path requirements rather than treating a proxy as completion.

Keep broader human-motion calibration, full network workbench, traffic alerts
and Linux in the roadmap with their existing distinct acceptance conditions.
Do not spend the next cycle adding generic authority scaffolding, broadening
the research collection, or rewriting the engine. Update only the source/docs
needed for each concrete milestone. A future Perspicuity adapter should emit
capture/resource evidence while Perspicuity owns durable archive/frontier
semantics; that consumer should not dictate the shared-browser UI lifecycle.

Before product implementation, turn the chosen next unit into the required
source-grounded sub-plan and independent review. This orientation does not
claim to have performed that design/plan tribunal.
